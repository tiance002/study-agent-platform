# ADR-013：技能与契约知识的版本治理

- **状态：** 已接受
- **owner：** 待指派
- **决策日期：** 2026-09-18
- **到期复审：** 2027-03-01

## 背景

平台运行时需要向模型按需提供技能与工具选择规则；设计与实施协作则需要按需提供领域契约（SQL 架构、协议、策略矩阵等）。此前两者都没有版本治理：

- 现有不变量 #13 要求「规则、策略、node、工具、验证器、数据集、提示词和模型配置版本必须进入决策记录」，但**未覆盖文档型知识**。
- 文档一旦被模型读取即成为指令，若不纳入版本，会出现「改了行为却找不到是哪次文档改动引起的」。
- 若把设计知识堆成单一长文，每次加载都挤占上下文；若只按模块拆文而无索引，模型只能猜文件名。

## 候选方案

| 方案 | 优势 | 劣势 |
|---|---|---|
| A. 单一长文档 | 无索引成本，不会找不到 | 上下文成本高，无法按需加载 |
| B. 按模块拆文档，无索引 | 单份小 | 「按需」退化为猜文件名，读错再读更浪费 |
| C. 分层 + manifest 索引 + 生成区／手写区双区 | 渐进披露、防漂移、扩展成本 O(1) | 需要维护生成脚本与校验门 |

## 已选方案

**C。** 具体规则：

1. 三层：L0 常驻（每次开工，≤1.5k token）、L1 领域契约（命中触发条件，单份 ≤4k）、L2 任务手册（任务触发，单份 ≤2k）。
2. `manifest.yaml` 为唯一索引入口，含 `id / layer / status / path / version / size_estimate / triggers / depends_on / expiry / generated_from`。
3. `status: planned` 为预留位，用于登记尚未编写的契约意图，保证扩展余地。
4. 依赖方向单向且无环；`active` 条目不得依赖 `planned` 条目。
5. L1 契约分**生成区**（代码导出，CI 比对不一致即失败）与**手写区**（人写，带 `expiry` 复审）。
6. **skill 与契约文档只改变「模型知道什么」，不改变「模型被允许做什么」**（不变量 #17）。

## 证据

- 不变量 #13 与 #17 的落点；`docs/skills/README.md` 的机械门清单。
- 首批只落三份契约（`sql-schema`、`protocol`、`tool-catalog`），用于验证机制本身；机制未验证通过前不补其余五份。

## 重新评估触发条件

- 单个 node 需读取超过 3 份契约，说明契约粒度偏细或 node 职责过宽。
- manifest 条目超过 25 条，索引本身超出 L0 预算。
- 生成区校验频繁误报（每月超过 2 次），说明生成脚本与源码组织不匹配。

## 回滚方案

将 `manifest.yaml` 降级为纯说明文件、契约合并为单份 L1 文档；L0 常驻层保留不变。回滚不影响任何运行时组件，因为 skill 不参与权限判断。
