# 分层架构、层间通信与模块契约

> **状态：** 讨论稿 v0，未并入正式规格。
> **前置：** 本文与 [Agent 技能分层、上下文管理与工具边界](./2026-09-18-05-agent-skill-context-and-tool-boundary.md) 配套。05 号定义"知识怎么组织"，06 号定义"模块怎么分层、层间怎么通信"。
> **解决的问题：** 现有设计中分层信息散在三处——部署单元（总设计 §3.2）、业务模块与"不负责"清单（总设计 §5）、代码目录（实施计划）——读者需要自行拼装，且**层间通信原语从未定义**，循环退出条件分散在三份文档中无法一眼看全。

## 1. 五层划分

| 层 | 职责 | 不负责 | 对应原业务模块 |
|---|---|---|---|
| L1 接入 | 展示、输入采集、流式呈现、确认交互 | 任何鉴权、权限或业务判断 | —（前端） |
| L2 边界 | 身份、租户与项目上下文注入、确定性授权、输入预检查 | 教学逻辑、模型调用 | Identity & Tenancy、Policy Gateway、Support & Privacy |
| L3 编排 | 会话与上下文装配、typed node 执行、预算树、子任务调度、暂停恢复 | 直接执行外部副作用、直接读写检索索引 | Conversation、Workflow Runtime、Learning Engine（计划与诊断部分） |
| L4 能力 | 模型路由、检索、工具与沙箱执行、验证器 | 决定权限，决定掌握状态 | Model Router、Knowledge Service、Tool & Sandbox Broker、Evidence & Evaluation（执行部分） |
| L5 事实 | 唯一真相源、事务、持久任务、outbox、对象存储 | 业务规则判断 | —（基础设施） |
| 旁路 A | 独立审计 sink | 参与主链回流 | Audit |
| 旁路 B | Evidence → Projector → 掌握投影 | 被 API 或模型直接写入 | Evidence & Evaluation（投影部分） |

**层与模块的关系不是一对一。** 层决定"依赖方向与通信原语"，模块决定"谁负责什么"。Learning Engine 横跨 L3（计划、诊断编排）和旁路 B（掌握投影写入），这不是设计缺陷，而是因为它本身承担两类不同性质的工作——但两者的进程、写入权和失败模式必须分开。

## 2. 层间通信原语（本文核心）

这是此前设计中缺失的一张表。**什么边界用什么通信方式，必须有统一规则，否则会出现"某些路径同步等待沙箱"这类违反延迟目标的实现。**

| 边界 | 原语 | 同步性 | 依据 |
|---|---|---|---|
| L1 ↔ L2 | HTTPS 请求 + SSE 流式回流 | 同步请求、流式响应 | 总设计 §7 |
| L2 → L3 | 同进程同步调用，**必须在同一事务内注入 `SET LOCAL`** | 同步 | 04 号 §2 |
| L3 → L4（轻读） | 同步调用，带 capability token 与预算 reservation | 同步 | 03 号 §3、§5 |
| L3 → L4（重活） | 写 durable task，worker 认领 | 异步 | 总设计 §7「长任务进入 durable task table」「交互请求不得同步等待沙箱」 |
| L4 → 外部系统 | ActionIntent → 幂等 dispatch → ToolOutcome → reconciliation | 异步 + 对账 | 不变量 #6 |
| L3 / L4 → L5 | 事务；跨边界用 outbox | — | 03 号 §9 |
| 任意层 → 旁路 A | 事件投递，高影响 fail-closed，低风险有界缓冲 | 异步 | 03 号 §9 |
| L4 → 旁路 B | append-only `EvidenceEvent` → Projector | 异步 | 01 号 §6 |
| L3 → ChildRun | spawn 子任务，父等待结构化信封 | 同步等结果 | 05 号 §4.4 |

### 2.1 层间禁止事项

- 禁止 L1 直接触达 L3 及以下——不得绕过边界层。现有文档的"用户无法通过 UI 绕过权限"属于此条。
- 禁止反向依赖：L4 不得调用 L3，L3 不得调用 L2 的内部实现。
- **禁止 L4 模块之间横向调用。** Knowledge 不能直接调用 Tool broker，必须经 L3 编排。理由：横向调用会让策略、预算和审计的注入点出现两个，等于多了一条绕过路径。
- 禁止跨层事件订阅。事件只在旁路 A / 旁路 B 方向流动。

### 2.2 为什么不用"以消息总线为中枢"的形态

参照图采用「以 MessageBus 为调度中枢的闭环」风格，本项目**不采用该形态**，原因是可证明性：

- 事件驱动擅长解耦，但**不擅长证明"什么也没发生"**。
- 本项目批次一的退出门要求「机械证明拒绝路径无外部副作用」。在纯事件驱动下，"拒绝"体现为"没有发布后续事件"，这需要遍历全部消费者才能证明；在分层同步调用下，"拒绝"体现为函数在关卡处 return，路径是有限且可穷尽的。

因此本项目采用**分层调用为主 + 局部事件为辅**：主链是确定性的同步调用序列，事件只用于旁路（审计、投影）和异步重活（摄取、沙箱、评测）。

## 3. 主链循环与退出条件

主链：用户 → L1 接入 → L2 边界检查 → L3 编排（解析 typed node、预留预算）→ L4 能力（路由、检索、工具）→ L5 事实回写 → 旁路审计与投影 → SSE 回流 L1 → 用户。

### 3.1 六类显式退出条件（此前散落四处，此处汇总）

| # | 退出条件 | 定义位置 |
|---|---|---|
| 1 | node 的循环、递归、并发、工具次数上限 | 03 号 §4 |
| 2 | 重规划次数上限（契约错、证据不足、越权三个分支） | 总设计 §6.2 步骤 8 |
| 3 | 预算耗尽：token、货币、步骤、并发、沙箱秒数 | 03 号 §5 |
| 4 | 澄清与拒绝分支终止（证据不足不通过升级模型解决） | 02 号 §2、§4 |
| 5 | 超时与 `unknown` 状态进入对账，不盲目重派 | 03 号 §6 |
| 6 | ChildRun 深度上限（首版 1 层，不可递归 spawn） | 05 号 §4.2 |

**门禁：六类出口都必须可观测、可测试。任一缺失即视为死循环风险，不允许通过批次门。**

## 4. 依赖方向与 CI 机械门

### 4.1 方向规则

```text
L1 → L2 → L3 → L4 → L5        主链，单向
旁路 A、旁路 B                  仅接收，不回流
```

### 4.2 CI 必须拦截的四类违规

1. **import 方向违规**：`knowledge ↛ learning.projector`、`model_router ↛ policy`（实施计划任务 1 已列），扩展到全层方向断言。
2. **工具重叠**：同一 `(intent_tag, sink_class, min_authority)` 下注册多个 `exclusive` 工具（05 号 §5.2）。
3. **skill 依赖成环或反向**：解析 manifest 的 `depends_on` 建图（05 号 §2.5）。
4. **跨层直接访问内部 ORM 或内部数据结构**：模块间只能通过有版本的服务接口与 schema。

## 5. 需要新增的两个模块

| 模块 | 所属层 | 职责 | 不负责 |
|---|---|---|---|
| Skill Registry | L3（供 L3/L4 查询） | 发布、版本化、按 node 声明下发技能与工具选择规则 | 权限判断、执行隔离 |
| ChildRun Runtime | L3 | 子任务 spawn、权限派生、深度与并发上限、信封校验 | 独立授权、A2/A3 副作用 |

两者都必须在总设计 §5 的模块边界表中登记，并各有 owner、版本与回滚方案。
