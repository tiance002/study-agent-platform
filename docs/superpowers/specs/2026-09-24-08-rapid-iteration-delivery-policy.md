# 快速迭代交付策略（Rapid Iteration Delivery Policy）

> 生效日期：2026-09-24
>
> 适用范围：Study Plan Agent 从当前原型到首个可用版本，以及首版后的数据驱动优化阶段。
>
> 本文只调整**交付优先级、退出门和缺陷处理方式**，不削弱现有系统不变量中的安全、隔离、数据完整性和副作用约束。

## 1. 目标

当前阶段的首要目标从“尽可能提前完成完整架构与优化”调整为：

1. 尽快交付普通用户可以完成的核心学习闭环。
2. 通过真实使用暴露真正的召回、记忆、上下文、性能和体验瓶颈。
3. 只对已被数据证明的瓶颈做针对性优化。
4. 允许非关键问题进入受控延期队列，避免长期卡在 Debug、边角优化和过早完备化上。

开发成功标准不是“零缺陷”，而是“核心路径可用、关键风险可控、已知问题可追踪、下一步有数据依据”。

## 2. 不可延期的硬门

以下任一问题存在时，不得作为“可控 bug”延期：

- 身份、租户、用户或项目隔离可能被绕过。
- 可能造成跨项目/跨用户数据泄露。
- 可能造成不可恢复的数据丢失、错误覆盖或迁移破坏。
- 可能产生重复收费、重复外部副作用、重复提交或无法对账的高风险状态。
- 可能伪造引用、把未验证结论标为已验证，或错误写入掌握度等核心学习事实。
- 核心用户路径无法完成，且没有可接受的临时替代路径。
- 会导致普通输入触发崩溃、死循环、资源无上限增长或明显安全问题。
- 会使已存在的核心不变量失去自动化测试或运行时断言。

这些问题属于 Release Blocker，必须先修。

## 3. “可控 bug”的定义

一个问题只有在**全部满足**以下条件时，才允许延期：

1. 不涉及安全、权限、租户/项目隔离、秘密、收费或不可逆副作用。
2. 不造成用户数据损坏或核心学习事实错误。
3. 不阻断“创建/进入学习项目 → 获取计划或教学 → 完成任务/反馈 → 保存结果”的主路径。
4. 影响范围明确，可稳定复现或明确说明触发条件。
5. 存在可接受的绕过方式，或者问题仅影响非核心体验。
6. 延期不会让后续修复成本显著扩大。
7. 已记录用户影响、已知边界、复现方法、临时方案和重新提升优先级的触发条件。

典型可延期问题：

- 非核心页面的样式、动画、文案和少量布局问题。
- 罕见格式解析失败，但用户可改用当前已支持的 Markdown/纯文本。
- 检索排序不够理想，但能找到关键原文且不会给出虚假引用。
- Token 或响应延迟高于理想值，但核心任务仍能完成且未突破预算。
- 某个高级上下文压缩、图谱检索、reranker、缓存策略尚未实现。
- 某个边缘浏览器或极少见输入的兼容性问题。

## 4. 缺陷等级

### P0 — Blocker

立即停止当前功能开发并修复。

适用：安全/隔离、数据破坏、重复收费或副作用、核心路径完全不可用、错误证据进入核心事实。

### P1 — Fix Now

当前里程碑内修复，但不一定中断正在进行的最小功能切片。

适用：主路径明显受损、无合理绕过方式、频繁崩溃、普通用户高概率遇到的严重体验问题。

### P2 — Controlled Bug

允许延期。必须登记并在下一次阶段复盘时重新评估。

适用：非核心路径、已有绕过方式、局部准确率或体验问题、有限范围技术债。

### P3 — Improvement

不算缺陷，进入优化池。

适用：性能提升、架构美化、进一步抽象、图谱增强、额外缓存、更多模型支持、更多格式支持。

## 5. 可控 bug 的管理字段

每个延期问题至少记录：

- `severity`: P2 / P3
- `user_impact`: 用户实际看到什么
- `scope`: 哪些功能/输入受影响
- `workaround`: 当前绕过方式
- `risk_check`: 是否涉及安全、隔离、数据、费用、引用、核心事实
- `evidence`: 复现步骤、日志、截图或测试
- `defer_reason`: 为什么现在不值得阻塞开发
- `promotion_trigger`: 什么数据出现时升级为 P1/P0
- `target_review`: 哪个里程碑重新评估

禁止只写“later fix”“known issue”而没有范围和触发条件。

## 6. 当前阶段的开发配额

在首个可用版本稳定前，默认把工程时间控制在：

- 70%：核心功能与端到端闭环
- 20%：必要测试、P0/P1 修复、发布硬门
- 10%：架构整理、性能优化和非阻塞重构

如果一个非阻塞 Debug/优化问题连续投入约 45 分钟仍没有明显进展，必须重新做一次 P0/P1/P2/P3 归类；P2/P3 默认停止深挖并登记。

该时间盒不是对安全/数据问题的限制；P0 必须解决。

## 7. 测试与审查策略

### 每个最小功能切片

只要求：

- 新功能的定向测试。
- 受影响模块的回归测试。
- 相关静态检查。
- 不变量相关改动必须有对应反例测试。

### 每个里程碑

再执行：

- 全量测试。
- PostgreSQL 端到端验证。
- 静态门和生成契约检查。
- 主用户路径人工/浏览器验证。

### 独立审查

不再把独立审查作为每个小功能的默认前置门。

只在下列边界强制：

- 身份/授权/RLS。
- 预算/收费/外部副作用。
- 数据迁移与恢复。
- 引用/证据升级到核心事实。
- 沙箱、网络、Secrets 等高风险能力。

其他功能可在里程碑末统一审查。

## 8. 设计与架构冻结规则

首版稳定前，禁止因为“以后可能需要”而新增大型子系统。

以下能力默认进入数据触发式优化池，而不是当前硬门：

- 完整四层记忆体系。
- 全量 Codex 式后台 memory consolidation。
- LightRAG/GraphRAG/独立图数据库。
- reranker。
- 多向量数据库或 Elasticsearch/Milvus。
- 完整 PDF/Office/OCR/VLM 摄取。
- 多 provider 适配。
- 100k 用户级高并发专项优化。
- 复杂缓存层和跨节点语义缓存。
- 完整可观测性平台。

只有满足以下至少一条才提前启用：

1. 当前里程碑被该问题直接阻塞。
2. 实际用户数据表明问题高频发生。
3. 冻结评测集证明现有能力达不到目标。
4. 性能/成本测量显示当前实现不可接受。

## 9. RAG 的当前交付策略

沿用 `keyword/v1` 作为可复现基线，不把语义检索当作首版前置条件。

升级顺序固定为：

1. 关键词 + 结构化标题/章节。
2. 收集真实召回失败样例。
3. 若同义改写或语义漏召回成为主要失败源，再加入 pgvector。
4. 只有离线评测证明有增益，再加入 reranker。
5. 只有跨文档关系成为明确瓶颈，再评估 LightRAG/GraphRAG。

不得跳级为了“架构先进”提前实现。

## 10. 记忆与上下文的当前交付策略

只做轻量版本：

- 保留原始会话，不让摘要覆盖原文。
- 长期记忆只存稳定、可复用、带来源的信息。
- 记忆默认按 `tenant_id + user_id + project_id` 隔离。
- 跨项目模板单独作为 reusable template，不混入项目记忆。
- ContextBuilder 只组装当前任务需要的项目状态、最近消息、少量相关记忆和必要 RAG 证据。
- 先做固定预算与简单摘要；只有真实长会话暴露问题后，再做复杂压缩/召回策略。

不在首版实现完整 Persona/Scenario 多级记忆体系。

## 11. 里程碑退出原则

一个里程碑可以带 P2/P3 问题退出，只要：

- P0 = 0。
- 与当前里程碑核心路径相关的 P1 = 0。
- P2/P3 全部有记录和范围。
- 核心流程有真实可重复的验收证据。
- 下一阶段的优化项来自用户反馈或数据，而不是主观猜测。

## 12. 与旧计划的关系

历史计划继续保留，作为实现与审查记录，不删除。

从 2026-09-24 起：

- 本文负责“哪些内容现在必须做、哪些允许延后”。
- 新的快速迭代计划负责“下一步按什么顺序交付”。
- 旧计划中的高级能力若与本文冲突，以本文的当前阶段优先级为准。
- 00 号系统不变量仍然拥有更高优先级，本文不得解释为降低安全和数据正确性要求。
