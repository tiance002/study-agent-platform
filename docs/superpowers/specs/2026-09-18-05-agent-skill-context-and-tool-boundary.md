# Agent 技能分层、上下文管理与工具边界

> **状态：** 讨论稿 v0，未并入正式规格。确认后需回改 00/02/03 号规格、补 ADR-013/014，并在实施计划中新增任务 9。
> **选题理由：** 现有六份规格覆盖了身份、策略、证据、检索、执行与治理，但**没有定义 Agent 运行时如何组织知识（skill）、如何管理上下文、如何隔离子任务**。只有 00 号规格把「MCP/skill 描述」列为不可信输入，未展开接入方式。这是当前设计的最大结构性空白。
> **读者：** 两批完全不同的消费者，见第 0 节。

## 0. 先划清两个平面

这是本次讨论最关键的前提。四条主张里，「skill 文档分层」主要落在平面 B，「子 agent / 工具边界 / MCP 复用」落在平面 A，两者**不能共用一套机制**。

| | 平面 A：平台运行时 Agent | 平面 B：设计与实施协作 |
|---|---|---|
| 消费者 | 学习助手本身（服务用户） | 编码/设计 agent（服务我们） |
| 知识载体 | 发布到 `SkillRegistry` 的版本化资产 | `docs/skills/` 下的 Markdown |
| 存什么 | 教学动作、工具选择规则、评估契约 | SQL 架构、领域模型、协议、策略矩阵 |
| 权限关系 | **知识绝不影响权限判断** | 无权限概念 |
| 版本治理 | 计入 `skill_registry_version`，进决策记录 | 计入 ADR 与实施计划版本 |
| 失败后果 | 教学错误、越权（若边界失守） | 设计漂移、实现返工 |

**判定规则：** 一份文档如果会改变「模型被允许做什么」，它就不属于 skill，而属于 registry 或策略表。skill 只能改变「模型知道什么」。

## 1. 四条主张的裁决

| 主张 | 裁决 | 必须附加的限制条件 | 若无限制会破坏的不变量 |
|---|---|---|---|
| 模块拆成 skill 文档按需加载 | **采纳** | 必须有 manifest 索引层；文档纳入版本治理；依赖单向无环 | #13 版本必须进入决策记录 |
| 工具边界明确、职责不重叠 | **采纳，但改做法** | 靠「唯一 owner 声明 + CI 机械检测」，不靠描述文字 | #5 未标注工具默认拒绝 |
| 子任务交子 agent，中间结果留在子上下文 | **采纳，但回传必须结构化** | 回传信封携带 lineage；摘要不得自动去 taint | **#10**（最危险，见第 4.4 节） |
| 积极复用成熟 MCP | **有条件采纳** | 协议复用、边界自建；schema 收窄并强制 taint | #9 外部内容不能改变权限、#10 |

## 2. 平面 B：设计知识的三层加载

### 2.1 分层与预算

| 层 | 内容 | 加载时机 | 目标体积 |
|---|---|---|---|
| L0 常驻 | 不变量摘要、术语表、当前批次门 | 每次开工 | ≤ 1.5k token |
| L1 领域契约 | 见 2.2 清单 | 命中触发条件时 | 单份 ≤ 4k token |
| L2 任务手册 | 见 2.3 清单 | 执行该类任务时 | 单份 ≤ 2k token |

**为什么必须有 L0：** 不变量只有被持续看见才有约束力。把 14 条不变量压缩成 1.5k token 的常驻摘要，比让人每次去翻 00 号规格有效得多。

### 2.2 L1 领域契约清单

| skill_id | 内容 | 触发条件 |
|---|---|---|
| `sql-schema` | 表、RLS 策略、约束、索引、迁移规则 | 涉及持久化、查询、迁移 |
| `domain-model` | 实体关系、`tenant_id`/`learning_project_id` 归属、生命周期 | 新增/修改实体 |
| `protocol` | API 契约、SSE 事件、错误码、typed node schema、状态机 | 定义接口或跨模块数据 |
| `policy-matrix` | L/A/D 三轴映射、obligation、失败方向矩阵 | 涉及授权、权限裁剪 |
| `tool-catalog` | 工具清单、`intent_tag`、`sink_class`、幂等与补偿语义 | 新增工具或排查选择歧义 |
| `evidence-rules` | EvidenceEvent、projection 约束、assessment contract | 涉及掌握度与验收 |
| `tenancy-rules` | RLS 装配、`SET LOCAL`、跨租户拒绝测试 | 涉及任何数据访问 |
| `egress-rules` | Fetcher/Package Proxy 边界、taint、endorsement | 涉及外部访问或依赖安装 |

### 2.2.1 清单不是封闭集合（扩展机制）

8 份是**首批清单，不是上限**。新增一份契约的成本必须保持 O(1)：

1. 在 `manifest.yaml` 增加一个条目（含 `layer`、`triggers`、`depends_on`、`expiry`）；
2. 新建对应文件；
3. 跑 manifest 校验。

**不需要修改 05／06 号规格，也不需要改任何代码。** 如果新增一份契约需要动到别处，说明分层设计有问题，应先修机制再新增。

保留扩展余地的具体做法：`manifest.yaml` 允许 `status: planned` 的预留条目——先登记意图与触发条件，文件后补。这样「想到但还没写」的契约有地方待着，不会被遗忘，也不会阻塞实施。

### 2.2.2 契约文档的双区结构（防漂移）

手写文档必然与代码漂移，因此每份契约固定分两区：

| 区 | 作者 | 内容 | CI 行为 |
|---|---|---|---|
| 生成区 | 代码导出（迁移、Pydantic schema、tool registry） | 表结构与约束、接口形状、工具清单 | 与源码不一致即**构建失败** |
| 手写区 | 人 | 使用说明、when-to-use、坑与例外 | 不校验内容，但必须带 `expiry` 到期复审 |

生成区带 `source_hash` 与生成时间；手写区变更更新 `version`。**机器可推导的部分不许手写。**

这既是「工具 registry 为真相源、`tool-catalog` 为生成视图」这条决策的通用形式，也是人读文档不被机器真相甩下的唯一可行办法。

### 2.3 L2 任务手册清单

`add-a-tool`、`add-a-node`、`add-a-migration`、`add-a-validator`、`add-a-prompt-combination`、`onboard-an-mcp-server`、`failure-drill`、`release-a-batch`。

每份手册必须包含：前置条件、机械校验命令、退出门、**失效条件**（什么情况下这份手册不再适用）。

### 2.4 manifest 规范

`docs/skills/manifest.yaml` 是唯一的索引入口：

```yaml
- id: sql-schema
  layer: L1
  path: contracts/sql-schema.md
  version: 1
  size_estimate: 3200        # token，超限需拆分
  triggers: [持久化, 查询, 迁移, RLS, 索引]
  depends_on: [tenancy-rules]
  supersedes_expiry: 2027-03-01   # 到期复审
```

**没有 manifest，「按需加载」会退化成「猜文件名」。** 模型先读 manifest（小、便宜），再决定读哪份契约（大、昂贵），这才是渐进披露。

### 2.5 依赖方向（CI 强制）

```text
L0 常驻 ──→ L1 契约 ──→ L2 手册
```

单向、无环。检测方式与实施计划任务 1 的 import 方向测试同构：解析 manifest 的 `depends_on` 建图，发现环或反向依赖则构建失败。

## 3. 平面 A：运行时上下文管理

### 3.1 四类上下文的可压缩性

| 类别 | 内容 | 可否压缩 | 规则 |
|---|---|---|---|
| 指令 | system prompt、node 声明的 skill | **否** | 按 `node_registry_version` 固定，运行中不可变 |
| 事实 | 项目状态投影、掌握度快照 | 可 | 只保留投影结果，不保留原始查询 |
| 证据 | 检索片段、工具输出、artifact 引用 | **只换指针，不压缩** | 压缩后必须保留 `source_id + span + content_hash` |
| 会话 | 消息历史 | 可 | 按 02 号规格的会话摘要机制 |

**核心规则：只有「会话」和「事实」可以为了省 token 而压缩；「证据」的压缩只能是替换为指针，不能是改写文本。** 一旦把证据段落改写成自然语言，taint 会继承到新值上（不变量 #10），引用溯源也随之断裂。

### 3.2 与现有规格的衔接

02 号规格已经要求「切换模型时使用结构化项目状态与会话摘要，而不是依赖某个模型的隐式上下文」。本节把它的适用范围明确到 node 级，并补充工具 schema 的按需加载：

- 低权限 node 不接收无关工具描述（03 号规格已有）；
- 该规则扩展到子 agent 与 MCP 包装层：**只下发当前 node 被授权且可能用到的工具 schema**；
- 单 node 常驻工具 schema 目标 ≤ 8 个，超过则说明 node 职责过宽。

## 4. 子 agent（ChildRun）规格

### 4.1 实体定位

`ChildRun` 是 `WorkflowRun` 的下级执行单元，**不是新的授权主体**。它继承父 run 的 tenant、project、node 上下文，只在父 budget reservation 内消费。

新增字段：`child_run_id`、`parent_run_id`、`parent_node_instance_id`、`depth`、`purpose`、`spawn_reason`。

### 4.2 权限派生（只减不增）

- 子 agent 的 capability token 由父 token 派生，**只允许收缩**。
- 子 agent 默认**只能持有 A0/A1**。需要 A2/A3 的动作必须回到主对话，走确认 UI。
- 子 agent 不可扩大并发、不可延长超时、不可调用父 node 未声明的工具。
- 子 agent 不可自行 spawn 子 agent；`depth` 硬上限为 1（首版），后续如需放宽必须走 ADR。
- 子 agent 是**不透明的**：主对话看不到它的工具调用过程，但审计记录完整旁路写入。

### 4.3 四类子 agent（职责互斥）

| 类型 | 唯一输出 | 权限上限 | sink | 禁止 |
|---|---|---|---|---|
| `research` | 带引用的发现集 | A0/A1c | 父对话上下文 | 写任何事实 |
| `extraction` | 符合 schema 的结构化字段 | A0/A1a | 父对话上下文 | 自由文本输出 |
| `verification` | 判定 + 理由 + 反例 | A0/A1a | 父对话上下文 | 修改被判定对象 |
| `drafting` | 待审 artifact | A0 | artifact 存储 | 直接 dispatch |

**互斥规则：** 一个子任务只能对应一个类型。若一个子任务既想检索又想写库，说明任务切分错了，必须拆成 `research` + 主对话执行。

### 4.4 回传信封（本节是最重要的修正）

「把最终结果汇总到主对话」若实现为让子 agent 用自然语言复述一遍，会同时破坏三件事：引用溯源、`display_policy` 展示、taint 判定。

**回传必须是结构化信封，不是散文：**

```jsonc
{
  "child_run_id": "...",
  "status": "ok | partial | failed | unknown",
  "artifacts": [
    { "source_id": "...", "span": [1024, 1780], "content_hash": "sha256:...",
      "parser_version": "...", "display_policy": "full | summary | citation_only" }
  ],
  "claims": [
    { "text": "...", "evidence_refs": ["artifacts[0]"],
      "kind": "sourced | inference",     // inference 不得用于掌握度证据
      "endorsement_scope": null }
  ],
  "taint": { "inherited": true, "new_sources": ["web"] },
  "unresolved": ["..."]
}
```

**四条硬规则：**

1. 自然语言只能是 `claims[].text`，且必须挂 `evidence_refs`；
2. 无来源的推断必须标 `kind: inference`，且不得进入 `LearningEvidence`；
3. `taint` 只能增加，不能因为「子 agent 看过了」而清除；
4. `status: unknown` 时主对话不得推断结果，必须走对账。

**一句话记住：上下文可以丢，谱系不能丢。**

### 4.5 上下文隔离 ≠ 证据隔离 ≠ 审计隔离

这三者经常被混为一谈，必须分开表态：

| 维度 | 子 agent 是否隔离 |
|---|---|
| 主对话上下文 | **隔离**（这正是目的：省 token） |
| 证据谱系 | **不隔离**（信封必须携带完整引用） |
| 审计记录 | **不隔离**（旁路写入，与上下文无关，不因压缩丢失） |
| 预算账本 | **不隔离**（从父 reservation 派生并实时结算） |

### 4.6 何时不该用子 agent

子 agent 有真实成本：上下文重建、token 重复、延迟增加、错误传播、用户看不到中间过程。

| 适合下放 | 不适合下放 |
|---|---|
| 上下文量大、只需结论（读 20 个文件做调研） | 需要与用户多轮澄清 |
| 可并行、互不依赖（多源检索、多文件解析） | 需要实时确认（A2/A3 副作用） |
| 输出可结构化校验 | 需要连续上下文（教学对话、逐步引导） |
| 失败可整体丢弃重来 | 延迟敏感（L0 路径 P95 < 200ms） |
| 只读（A0/A1） | 有副作用、需要 intent 与对账 |

**经验阈值：** 子 agent 的启动开销约等于「system prompt + 工具 schema + 必要上下文」的重建，量级在 1–3k token。**预计任务本身消耗低于 3k token 时不开子 agent**，直接在主对话做更便宜。

## 5. 工具边界：唯一 owner 与机械重叠检测

### 5.1 现有设计的缺口

03 号规格已要求工具定义「参数 schema、网络/文件边界、幂等、补偿、审计级别」，但**没有声明「这个工具是干什么用的」的机器可读标签**，因此重叠只能靠人看，无法机械拦截。`search_knowledge` 和 `read_source_span` 都能返回内容片段时，模型只能随机选。

### 5.2 工具声明扩展字段

| 字段 | 含义 | 作用 |
|---|---|---|
| `intent_tag` | 唯一的「动词 + 宾语」，如 `retrieve_chunk` | 重叠检测主键 |
| `sink_class` | 结果写向哪里：`context` / `artifact` / `external` | 区分同名不同用途 |
| `owner_module` | 唯一负责模块 | 禁止跨模块重复实现 |
| `min_authority` | 最低权限档位 | 权限裁剪 |
| `exclusivity` | `exclusive` / `composable` | 是否允许多工具完成同一 intent |

**重叠检测规则（CI 机械门）：** 同一 `(intent_tag, sink_class, min_authority)` 组合下注册了多个 `exclusive` 工具 → 构建失败。这条规则能拦下绝大多数「模型不知道该调哪个」的问题。

### 5.3 歧义修复顺序

发现两个工具功能接近时，**按此顺序处理，不要跳到最后一步**：

1. **合并** —— 最常见且正确的答案：它们本就该是一个工具；
2. **降为内部函数** —— 其中一个不该暴露给模型；
3. **拆分参数** —— 用参数区分而非用工具区分；
4. **补描述文字** —— 最后手段，且必须同时写入 `tool-catalog` 的 when-to-use 表。

**反模式：** 一发现模型选错工具就加长描述。描述越长，schema 越贵，选择反而越差。

### 5.4 选择规则表的归属

「什么时候用哪个工具」属于知识，不属于策略。它写入 `tool-catalog`（L1 契约），随 node 的 skill 声明一并下发，**不写死在 system prompt 里**——否则每次新增工具都要改 prompt 版本。

## 6. MCP 复用策略

### 6.1 总原则

**协议复用，边界自建。** MCP 解决的是「怎么连」，不解决「能做什么」。findings 已经指出「MCP reference server 仅可作为参考实现，不能默认具有生产级隔离和可靠性」，本节把它落成准入门槛。

### 6.2 准入清单（全部满足才接入）

- [ ] 工具集合有限且有明确边界（不接受「万能 shell」类 server）
- [ ] 每个工具可声明幂等语义或可查询对账
- [ ] 版本可固定（commit 或版本号），许可证已核验
- [ ] 无隐式出网，或其出网目标可被白名单约束
- [ ] 响应大小可限制
- [ ] 维护状态与 owner 明确

不满足任一项 → 包一层自建边界，或直接自建。

### 6.3 包装层要求

1. **重命名收窄**：MCP 工具名映射为内部 `tool_id`，参数 schema 以内部契约为准（超集参数一律剔除）；
2. **文本字段强制 taint**：MCP 返回的一切文本视为外部内容，默认 `tainted`；
3. **无幂等声明 → 最高只给 A1**，不得进入 A2/A3；
4. **响应大小与超时上限**，与 `tool-catalog` 声明一致；
5. **`tools/list` 描述不可信**：不得直接进入 system prompt 或作为策略输入（不变量 #1、#9）；
6. **schema 按需加载**：只向被授权且可能使用的 node 下发，避免一个 server 的几十个工具定义挤占主对话上下文。

### 6.4 不接入清单

远程代码执行类、无边界文件系统类、自动发布/支付类、无法固定版本或上游描述频繁变动类、需要长期凭据且无法收窄 scope 类。

## 7. 扩展性检查清单

新增任何能力前，逐条回答：

1. 它属于平面 A 还是平面 B？
2. 它的 `owner_module` 是谁？是否与现有模块职责重叠？
3. 它是知识还是权限？若两者都有，切开。
4. 它的上下文体积是多少？在 L0/L1/L2 哪一层，或走子 agent？
5. 它的 `intent_tag` 是什么？是否与现有工具冲突？
6. 它需要什么权限档位？是否有 A2/A3 成分需要确认流程？
7. 它的版本号进哪个 registry？回滚方式是什么？
8. 它失败时的失败方向是 fail-closed 还是 fail-open？在失败矩阵哪一格？

**任何一条答不上来，就不该进入实施。**
