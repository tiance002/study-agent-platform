# 第七轮复审

审查基线：`44904d4bc4af6b941fd9ecb5413ba90963a93e37`。本次仅审查及规划，不修改业务实现。

结论：第七轮尚未达到普通用户闭环退出门。此前完成记录和全绿结果不能支持该结论，应以本次发现修正完成判定。这里是工作台及其直接依赖的定向审查，不是第一至六轮全部安全逻辑的重新认证。

## 确认的问题

### R7-01 / P1：保存已有计划会替换成不完整计划

- 位置：`frontend/app.js:125,283-290`；`backend/app/api/product_routes.py:276-299`。
- 编辑表单只装入目标和第一里程碑标题，提交固定只有一个里程碑，description 为空，tasks 为空。服务端明确按整版替换处理。
- 有多个里程碑或任务的计划，用户只改目标再保存，当前计划就不再包含其余结构。历史版本仍保留，不等于数据库历史被物理删除。
- 修复方向：本轮先限制已有计划为只读；无计划时允许创建完整初始计划。若需要编辑已有计划，必须单独设计保留任务身份/证据和版本冲突的接口，不能把旧 GET bundle 直接传给当前 PUT。

### R7-02 / P1：异步回包没有项目、会话及用户隔离

- 位置：`frontend/app.js:97-138,151-168,190-203,244-254`。
- 项目加载、消息加载和轮询完成后直接更新全局 state，没有取消或代次检查。切换项目/会话不会清空 activeRun；退出也未清空运行、消息、草稿等全部状态。
- 慢请求在切换后到达，会把旧消息/计划/运行写入新工作区；旧计划与新 projectId 组合还可能造成错误保存。此处是前端过期状态污染，不是已证明服务端越权。
- 修复方向：所有异步写 state 统一校验用户、项目、会话作用域和请求代次；切换同步清理旧数据；退出清理并使全部在途回调失效。

### R7-03 / P1：手机无法创建首个项目

- 位置：`frontend/app.css:136,146`；`frontend/app.js:372`。
- <=720px 把唯一创建项目表单 display:none；空状态按钮只尝试 focus 隐藏输入框。<=1080px 还隐藏唯一证据栏，没有替代入口。
- 新手机用户登录后无法开始学习闭环，已有用户也无法查看证据。

### R7-04 / P2：刷新只取一次运行状态，不恢复轮询

- 位置：`frontend/app.js:159-174,244-275,325-338`。
- 恢复 effect 只 GET 一次；pollRun 仅由发送问题调用。刷新发生在 queued/running 时，界面不会继续跟踪到终态；工作区刷新按钮也没有读取运行。
- localStorage 仅按项目保存最后运行指针，未保存当前项目/会话选择。临时 GET 失败还直接删除恢复指针。

### R7-05 / P2：引用回读和摄取状态未实现

- 位置：`frontend/app.js:301-319,470-495`。
- 上传返回的 document/job 被丢弃，未调用 ingestion-jobs 状态端点；资料一律显示“已登记”。引用仅显示 source_id、坐标和 hash，没有原文读取操作；未调用 span 接口。
- succeeded 一律标为“回答已核验”，即使 grounding 不含已核验来源。完成生成、来源坐标校验、语义真实性必须区分。
- 这些与第七轮已勾选的摄取任务状态、引用回读退出门不符。

### R7-06 / P2：204 响应错误地携带 null 正文

- 位置：`backend/app/api/product_routes.py:309,640`。
- JSONResponse(status_code=204, content=None) 实际 body 为 b'null'。h11 对 204 发送该 body 会抛出 LocalProtocolError，真实 HTTP 服务可能出现连接关闭与错误日志；不能因 TestClient 接受响应就忽略。
- 本次在项目虚拟环境复现：创建相同 JSONResponse，将 status/headers/body 顺序交给 h11 SERVER 的 Response 和 Data，得到 `Too much data for declared Content-Length`。
- 应使用空 Response(status_code=204)，并验证真实 HTTP 连续请求与日志。

### R7-07 / P2：响应丢失后重试使用新幂等键

- 位置：`frontend/app.js:19-26,207-224,258-280`。
- 每次 api 调用随机生成 key。请求已提交但响应丢失，用户按提示重试会生成新 key；后端无法识别同一逻辑提交，可能重复创建项目/教学运行并重复消费预算。
- loading 只限制当前等待期间点击，不处理未知结果。需要保留逻辑命令的 key、payload 和结果状态，重试复用相同 key；用户明确新建另一条命令才生成新 key。

## 为什么测试全绿仍然漏错

- `backend/tests/test_frontend_assets.py` 只测静态资源和脚本字符串，不执行用户行为。
- `tools/check_round7_browser.py` 的教学断言是“教学服务尚未启用”，没有成功回答、引用读取、刷新恢复、并发切换或请求重放断言。
- 手机用 browser.new_page 新建独立上下文，未登录，仅检查登录页没有横向滚动；不能证明手机工作台可用。
- 内存预览无法证明 PostgreSQL 重启持久化；ASGI TestClient 不覆盖真实 HTTP 协议写入。
- `tools/run_round6_gate.py` 只判断 pytest 退出码，未要求 PG 用例实际执行数大于零且零 skip。
- 根因是“需求 -> 场景 -> 断言 -> 证据”链条缺失，不宜归结为个人能力或模型名称。更长的计划只有绑定可失败断言和独立复核才有用。
