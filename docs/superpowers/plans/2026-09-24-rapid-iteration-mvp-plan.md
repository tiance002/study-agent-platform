# Study Plan Agent 快速迭代 MVP 计划

> 日期：2026-09-24
>
> 目标：停止继续横向扩架构，用最少新增机制尽快交付普通用户可实际使用的学习闭环；随后由真实场景与测试数据决定 RAG、记忆、上下文、性能和并发优化。

## 0. 当前判断

仓库已经具备较强的安全、持久化、幂等、摄取和教学运行底座，但普通用户首版仍缺少真正顺滑的产品闭环。

因此下一阶段不再按“基础设施能力清单”推进，而按“用户能否完成学习任务”推进。

### 立即降级为非阻塞项

- LightRAG/GraphRAG。
- reranker。
- 完整语义检索调优。
- 完整 Codex 式 Memory 两阶段后台流水线。
- 腾讯 Agent Memory L0-L3 全层复刻。
- 多 provider。
- PDF/Office/OCR 全格式覆盖。
- 大规模高并发专项调优。
- 完整监控平台。
- 非核心 UI 精修。
- 每个小任务都做独立审查。

以上能力只有真实数据证明需要时才升级。

## 1. Milestone A — 可用首版闭环

### 用户必须能完成

1. 进入系统并拥有自己的学习项目。
2. 创建或选择一个学习目标。
3. 完成基础诊断或输入已有基础。
4. 获得一份可执行学习计划。
5. 在会话中提出学习问题并得到回答。
6. 关联已有学习资料并看到可核验引用。
7. 完成任务/提交反馈。
8. 系统保存计划、任务、会话与学习证据。
9. 重新打开后状态仍在。

### 技术范围

只实现上述路径直接需要的能力。

RAG：
- 保留现有 `keyword/v1`。
- 不因没有 pgvector/reranker 阻塞首版。

Memory：
- 只实现 user/project scoped memory 的最小结构。
- 只保存稳定事实、目标、约束、明确偏好和重要决定。
- 必须记录来源；不把模型推断直接升级为用户事实。

Context：
- 一个简单 `ContextBuilder`。
- 输入 = 当前项目状态 + 当前任务 + 最近消息 + 少量相关记忆 + 必要证据。
- 设置明确 token 上限。
- 原始会话永远保留。

Frontend：
- 只做核心路径需要的 React 页面。
- 视觉精修、动画、复杂设置页均延后。

Provider：
- 有可用凭据时接一个正式 provider。
- 无凭据时允许 ScriptedProvider/模拟器继续推进 UI 和业务闭环。
- “真实 provider 未验收”必须明确显示为已知限制，但不阻塞其他首版工作。

### Milestone A 退出门

必须满足：

- 主用户路径可从头走到尾。
- P0 = 0。
- 核心路径 P1 = 0。
- 数据重启可恢复。
- 租户/项目隔离仍成立。
- 引用不伪造。
- 已知 P2/P3 有记录。

不要求：

- 最优召回率。
- 最低 Token。
- 最低延迟。
- 完整格式支持。
- 大规模并发证明。

## 2. Milestone B — 真实场景验证

核心功能稳定后，不立即继续堆功能。

先收集真实使用样例，至少记录：

- 用户任务是否完成。
- 哪些问题回答失败。
- 哪些失败来自“没召回”。
- 哪些失败来自“召回了但模型没用好”。
- 哪些失败来自“上下文缺失/污染”。
- 哪些失败来自“计划本身不合理”。
- 输入/输出 token。
- 总响应时间与主要耗时阶段。
- 用户是否需要重复解释自己的目标/约束。
- P2/P3 bug 的实际触发频率。

### 该阶段只做两类开发

1. P0/P1 修复。
2. 能直接改善真实失败样例的最小修改。

禁止因为“看起来会更好”引入大组件。

## 3. Milestone C — 数据驱动优化

根据 Milestone B 的数据选择分支。

### 如果主要问题是召回漏失

先加：

`PostgreSQL + pgvector + keyword/vector fusion`

然后在冻结测试集比较：

- Recall@K。
- 关键证据覆盖。
- 错误引用率。
- Token 增量。
- 延迟增量。

只有有明确收益，再考虑 reranker。

### 如果主要问题是跨知识关系

先检查现有 `knowledge_nodes + knowledge_edges` 是否足够。

只有普通关系表 + Hybrid RAG 无法解决时，再评估 LightRAG。

### 如果主要问题是记忆污染

优先修：

- scope。
- source provenance。
- 冲突/失效状态。
- 跨项目读取规则。

不是先增加更多记忆层级。

### 如果主要问题是长上下文/Token

优先做：

- 更严格 ContextBuilder 预算。
- 旧消息摘要。
- 原文指针回查。
- Memory Top-K。

只有真实长会话仍频繁丢关键信息，再引入更复杂的 Codex 式 consolidation。

### 如果主要问题是吞吐/延迟

先 profile，再优化。

只有测量证明数据库、检索、模型、SSE 或 worker 中某一处是瓶颈，才做并发专项优化。

## 4. 开发节奏

每个功能切片控制在“可以独立演示和验收”的规模。

推荐顺序：

1. 先实现最短端到端路径。
2. 写最小定向测试。
3. 手工跑一次真实场景。
4. 发现 P0/P1 立即修。
5. P2/P3 记录后继续。
6. 到里程碑再跑全量门禁。
7. 收集用户反馈。
8. 决定下一批，而不是一次规划未来全部实现。

## 5. Debug 时间盒

非安全、非数据、非核心路径问题：

- 连续 Debug 约 45 分钟没有明显进展，暂停。
- 重新判定 P0/P1/P2/P3。
- 若为 P2/P3，记录已知事实、失败尝试和下一触发条件后继续主线。

安全/隔离/数据/费用/引用正确性问题不适用时间盒，必须解决。

## 6. 测试策略调整

### 功能开发中

跑：

- 新增/修改模块测试。
- 直接依赖模块测试。
- 相关不变量测试。

### 里程碑前

再跑：

- 全量 pytest。
- PG E2E。
- Ruff / mypy。
- 生成契约校验。
- 迁移往返（如果本阶段动了 schema）。
- 浏览器主流程。

避免每改一个小函数就重复运行所有高成本验收。

## 7. Pull Request / 审查策略

小型低风险修改：

- 自测 + 定向 review 即可。

高风险修改才要求独立审查：

- auth / RLS / permission。
- budget / billing。
- durable side effects / idempotency。
- migrations。
- citation / mastery evidence。
- sandbox / fetcher / secret。

## 8. 第一批具体工作

优先级顺序：

### A1. 普通用户入口

让用户不需要终端命令即可进入并创建学习项目。

### A2. 核心学习闭环前端

把已有诊断、计划、任务、教学会话、资料引用能力串成最小 React 流程。

### A3. ContextBuilder v0

加入：
- 当前项目。
- 当前任务。
- 最近消息。
- 当前项目关键事实。
- RAG 证据。
- 固定 token budget。

### A4. Memory v0

只实现：
- user scope。
- project scope。
- source_message_id。
- type。
- status。
- updated_at。

暂不 embedding memory、不做 Persona/Scenario 多层 consolidation。

### A5. 真实场景记录

加入最小指标：
- request id。
- total latency。
- provider latency。
- retrieval latency。
- input/output token。
- retrieval hit count。
- failure category。

不建设完整可观测性平台。

## 9. 明确不做

在 Milestone A 结束前，默认禁止主动开启：

- 新图数据库。
- 微服务拆分。
- Redis/消息系统替换。
- LightRAG 正式接入。
- reranker。
- 多 embedding 模型。
- 自动记忆图谱。
- 复杂 Persona。
- 大规模 benchmark 基础设施。
- 全格式文档解析。
- UI 设计系统重做。

如需破例，必须在任务中写出“当前主路径为什么被它阻塞”。

## 10. 交付节奏

每个阶段交付一个用户可感知的版本：

- A：能完整使用。
- B：真实使用并收集失败案例。
- C：针对最痛的 1-2 个瓶颈优化。
- D：再次实测，再决定下一轮。

不再提前一次性实现所有“未来可能需要”的优化。

## 11. 成功标准

本计划的成功不是测试数量增长，而是：

- 从需求到可演示功能的周期明显缩短。
- 用户可以更早开始实测。
- Debug 时间不再被低优先级边角问题吞噬。
- 架构变更由真实问题触发。
- 每一轮都能说清楚：本轮解决了哪个真实用户问题。
