# 学习规划平台交付路线、代码审查与测试评估

评估日期：2026-09-25。代码基准：`b0afdb2486a83381c384d43dd2ca01e53ac64914`。近期审查基线：`c28817e`。本报告针对当前工作树与可执行的本地验收；历史生产记录仅作为背景，不代表当前版本已经发布。

## 结论与边界

**建议继续用现有 FastAPI + React 交付产品，现阶段不把 Dify/Langflow 接入正式交付链。** 新增低代码平台具备技术可行性，但不是首版交付的必要条件。现有代码已实现持久化教学、权限、预算、检索、引用、前端学习闭环等关键部分，剩余工作主要落在业务质量、真实模型、生产升级和验收。Dify可更快搭建一条工作流原型，却不能代替项目身份隔离、学习状态、证据、预算和恢复语义；为保留这些不变量所需的适配和运维成本，在当前仅有一个优先工作流的情况下大于节省的编排代码。

按**一名熟悉仓库的开发者、每周约30小时有效开发、需求冻结、模型凭据和部署权限已备齐**估计，下文定义的可交付产品 v1：纯现有架构约 **22–37 个工作日，含约20%缓冲为 27–45 个工作日（约6–9周）**；FastAPI + Dify 混合架构约 **27–45 个工作日，含缓冲为 33–54 个工作日（约7–11周）**。这是任务分解的规划估算，不是历史速度实测或固定承诺。若单人每周只投入15小时，日历周数大致翻倍。按当前范围，现有开发方式预计快约 **1–2周**；差异小于未知事项的误差带，首次真实模型与目标服务器验收可改变绝对日期。

若2026-09-28开始、每周工作5天且不计法定假期，现有路线的规划交付窗口约为**2026-11-03至11-27**，Dify混合路线约为**2026-11-11至12-10**。这些是工时换算出的条件日期，不是发布承诺；中国法定假期、真实模型接入和旧数据库处置将移动窗口。

这里的“最终产品 v1”按已批准的快速交付目标冻结为：新用户可注册登录、建立项目和目标、诊断、获得可执行计划、完成资料关联和带可核验引用的教学问答、推进任务并保留自报与真实证据差异、重登/重启读回；真实模型调用、数据隔离、预算、备份恢复、关键浏览器路径、P0/P1 清零及生产发布完成。若“最终产品”还要求语义向量、分层混合检索、重排序、多级本地/云路由、可验证工具执行和长期记忆完整体，则它是另一阶段，估计还需 **25–45 个工作日**，两路线都不应把它算入 v1。该阶段 Dify 是否更快必须以冻结的样例集和一条等价工作流实测，不能由平台功能清单推断。

在“最终产品”指**附件全部增强项也完成并验收**的更大口径下，先暂按两条路线各增加25–45有效工作日估算：现有架构累计约**52–90工作日（11–18周）**，Dify混合架构约**58–99工作日（12–20周）**。若2026-09-28开工、按每周5天且不计假期，条件日期分别约为**2026-12-08至2027-01-29**与**2026-12-16至2027-02-11**。高级RAG和路由尚无冻结质量样例或平台试验，扩展阶段的估算置信度低于v1；它不能作为提前引入平台的确定收益。

| 比较点 | 继续现有代码 | 增加 Dify（合理方案为混合架构） |

资源投入方面，两方案都需要一名熟悉现有Python/React/PostgreSQL边界的开发者、真实模型调用额度和生产发布/运维时间。Dify混合方案的上述27–45有效工作日已包含部署与适配，后续还需要维护该平台；部署时需核对官方至少2核4GiB的机器要求及默认依赖服务，若与现有业务同机，实际所需余量要实测。具体云账单、模型Token费用和机器能否共用尚无规格或报价，不能填造金额。若团队已有可复用的Dify环境和熟练维护人，工期表中的平台部署工作可下降，但仍须完成同一业务验收。

Dify的[外部知识API](https://docs.dify.ai/en/cloud/use-dify/knowledge/external-knowledge-api)和[Docker Compose部署要求](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose)说明“可以集成”在技术层面成立。外部知识API目前的请求含 knowledge ID、query、检索参数及可选元数据条件；这些字段不是用户身份凭证。官方的[可视化工作流入门](https://docs.dify.ai/en/guides/application-orchestrate/creating-an-application)证明流程编排便利，但不能据此保证本系统的业务等价性。Langflow也支持[Docker部署](https://docs.langflow.org/deployment-docker)和[自定义Python组件](https://docs.langflow.org/develop-application)；现有项目Python业务层已经较完整，把更多逻辑搬进组件会引入第二个代码运行边界，现阶段无明显工期优势。

**可以保留一个有条件的实验入口**：v1稳定后，用一个独立的“目标→结构化计划”工作流做最长3–5天的试验，同一组至少30个真实目标，比较结构有效率、学习任务可执行率、95分位延迟、单次费用和开发总工时。试验不改变权威业务数据归属；若节省的已验证工时大于接入与持续运维工时，再写架构决策并引入。RAG、工具与路由优化不应成为这次实验的前置条件。

## 代码审查发现

审查依据为项目`docs/skills/L0/invariants.md`的身份/租户/项目隔离、证据真实性、预算和失败显式化规则；覆盖近期 `c28817e..HEAD` 差异、相关接口/仓储/迁移/前端、生成契约及后端全量门禁。对vendor压缩包、历史未改动代码和生产机器未作逐行审查；此处“全面”指模块和关键用户/安全路径覆盖，不声称无遗漏。

按变更模块复核的范围是：身份与认证（6个变更文件）、学习/产品（4个）、知识库/摄取（4个）、数据库适配器（4个）、API（5个）、前端（13个，vendor仅核资源引用与许可证）、数据库基线（20个旧迁移删除/新迁移相关差异）、工具与门禁（10个）、测试（34个）以及文档/配置（14个）。代码检查重点是跨层接口、权限、事务、幂等、状态机和刷新后的用户行为；现有986项测试和契约/迁移检查提供未逐行读取路径的机械覆盖。下列发现是经代码追踪或运行复现的具体缺陷；未发现新的租户隔离绕过或审计/预算P0，但这不等于形式化安全证明。

### P1：发布前应处理

1. **知识库URL关联在已选候选上失败。** [library_routes.py](../../backend/app/api/library_routes.py) 的 `_find_or_discover_candidate` 把同URL/同标题的 `SELECTED` 候选复用，而下载状态机仅对同一个 `library-attach:{source_id}` 幂等键返回旧任务。用户先从项目候选选择URL，再把同URL同标题登记到知识库并关联项目，返回`403 ILLEGAL_STATE_TRANSITION`。在当前HEAD的内存 HTTP 路径已复现：注册201、创建候选201、选择202、登记库材料201、关联403；项目资料关联不完成。应只在确实属于同一库关联任务时复用SELECTED候选，否则新建/转为合法候选，并对内存与PG都加交叉路径回归。

2. **库内材料版本回执与项目实际副本可能不一致。** [library_routes.py](../../backend/app/api/library_routes.py) 两次读取最新版正文和版本号，各自独立事务；并发上传一版时可能将旧正文与新版本号配对。已经存在的确定性不一致是：库内新增第2版后再次关联，仓储直接复用第1版活跃摄取任务，却仍返回`library_document_version=2`（现有测试刻意锁定这一行为）；[library.py](../../backend/app/knowledge/library.py) 又宣称“重新关联可拿新版本”。引用哈希校验本身仍以项目实际副本为准，但回执不能准确说明使用了哪个版本。应把内容与版本作为同一快照读取，并将`library_document_version`定义为**实际关联副本版本**；若支持显式更新项目副本，应新增带版本前置条件的单独命令和回归测试。

3. **生产升级路径尚未闭合。** [platform.py](../../backend/app/platform.py) 期待数据库版本`0001`，而[部署手册](../../deploy/production/README.md)记录ECS为旧迁移`0013`。本轮未连接生产机核对其现状；现有计划只做空库新基线，不支持旧库原地升级。若实际库仍是旧版本，直接部署新程序将被启动自检拒绝；先确认生产库实际版本，按已选数据保留/放弃策略完成备份、独立空库初始化、切换及回滚演练，并对目标环境做真实用户验收。此项是**发布阻断差距**，不是本地测试失败。

### P2：可在P1之后修复或登记

4. **密码前后端按不同长度单位计数。** [views.js](../../frontend/views.js) 的 `maxLength:12` 在Chrome/Edge按UTF-16码元限制，后端[passwords.py](../../backend/app/identity/passwords.py)明确允许6–12个Unicode码点。两种浏览器真实输入7个emoji都只留下6个，用户无法输入其合法原口令。可在前端按`Array.from(value).length`验证码点且避免HTML码元上限误截；注册和登录应共享规则。

5. **已完成任务仍给出不可用的提交入口。** [views.js](../../frontend/views.js) 用`status !== "pending"`决定展示提交按钮，`done/skipped`也会显示；后端[loop_store.py](../../backend/app/learning/loop_store.py)只接受`in_progress`。用户在已完成任务上填写内容会稳定被拒绝。按钮条件改为`status === "in_progress"`并保留服务端状态门。

6. **知识库列表异步刷新可能因切项目而被丢弃。** [project-state.js](../../frontend/project-state.js)以包含项目/会话的`scopeRef.epoch`守护主体级列表请求。请求未完成时切换项目会改变epoch，结果被丢弃；[app.js](../../frontend/app.js)的刷新effect只依赖账号，通常不会再拉。需只按`principalId`或独立账号代次守护；用延迟HTTP响应+切项目浏览器用例证明旧账号数据仍不可见且同账号结果不丢。当前为代码路径判断，尚无本轮浏览器复现，优先级低于已复现的三项。

已确认的正确方向：用户级资料与项目资料分开建模；数据库RLS与应用端成员校验共同保护读取；资料原文、结构元数据、检索索引的权威边界没有因附件而改写；自报为中性裁决，引用由冻结快照核验。代码质量方面，平台组合根仍较大、前端依赖大包vendor、CI未覆盖浏览器和进程恢复，分别已有`docs/tech-debt.md`记录；在v1前不应仅为重构美观扩大任务。完整工具白名单/预算路径属于旧核心代码，现有不变量测试可验证已有机制，**不能把它当成Dify工作流已经落地**。
