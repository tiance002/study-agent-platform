# 6sol 第 1 次审查：指标架构调研报告

## 审查结论

**状态：设计需要用户确定；实现尚未开始。**

6luna max 按 brief 完成了只读勘察，没有改产品代码、没有运行测试。它正确识别出：获取耗时在 fetch 进程内、获取 worker 与 Web/教学进程分离、生产没有 acquisition systemd unit、项目没有跨进程 metrics 收集器。此时若只加 Python 进程内 Counter，会丢失 worker 指标并错误宣称已解决全局采集，因此停止符合 brief。

## 方案审查

### A. PostgreSQL 持久化 + 内网指标读取（推荐）

- 与项目现有生产架构一致，跨 worker、进程重启和 Web 抓取都能使用同一数据源。
- 需要新增受约束的持久化指标事实及安全聚合读取路径；必须保持 `study_app` 与 `study_worker` 最小权限，聚合端不得回传 ID 或业务正文。
- 只写迁移与代码，不运行迁移、不连接或改动生产数据库、不部署；公网 nginx 必须阻止或认证 `/metrics`。
- 这是满足“获取与路由指标”且不依赖尚不存在的日志采集器的方案。

### B. 结构化 journald 事件

- 低成本且能复用 systemd 收集的 stdout；可记录时延、字节和闭合 outcome。
- 目前没有日志转指标解析器/exporter，因此只有事件，不是跨进程聚合指标或 Prometheus scrape endpoint；acquisition worker 也尚无生产 systemd unit。
- 可作为临时排障日志，不能宣称首轮的全局指标验收通过。

### C. 共享文件 spool

- 可以避免 DB 迁移，但要额外设计跨进程写锁、去重、重启恢复、文件权限和日志轮转；仅支持当前单机，且与现有共享 runtime volume 形成新的状态机制。
- 相对 PostgreSQL 更难保证恢复与运维，因此不推荐。

## 具体审查发现

- 当前没有可以捕获 fetch duration 的持久记录；artifact 的 `fetched_at` 只有墙钟时刻，不能代替耗时。
- artifact 恢复路径不产生新的外部 fetch，指标必须将其排除。
- 现有路由快照和 provider usage 已在 Postgres 有可靠事实来源；usage `NULL` 代表未知，不能算成 0。
- 指标响应应只包含聚合数字和闭合枚举；所有资源 ID 只能用于内部幂等关联，不能出现在 labels 或响应中。
- 当前生产文档仍指向迁移 `0013`；R9 的 `0015`–`0017` 还在未提交工作区。这一轮只能新增迁移文件，不得实际执行。
