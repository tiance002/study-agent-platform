# Study Plan 快速交付开发

## 目标

推动一个范围清楚、用户可用、经过适当验证的功能闭环。优先级依次是：数据与访问边界正确、当前主流程可用、接口和架构边界稳定、相关验证充分，然后再处理非阻塞边缘问题和专项优化。

本技能提供开发指导，不改变项目运行时的授权、工具权限或用户给出的范围。

## 开始任务

对需要改代码的任务，先用与任务规模相称的简短说明明确目标和验证。局部小改动只需写清 Goal 与 Validation；涉及多层或重要边界时再补充适用的字段，不要为了填模板扩大分析：

```text
Goal: 本次交付的用户能力或缺陷修复结果
Invariants: 3～7 条不可破坏的约束
Scope: 本次需要修改的模块
Out of Scope: 当前明确不处理的事项
Contract: 仅在涉及 API、数据模型或错误语义时列出
Acceptance: 1～5 条可判断的完成条件
Validation: 与变更风险匹配的最小验证
```

从能贯通主流程的最小切片开始。普通功能尽量限制在少数模块；如果范围扩展到多层，先确认每一处修改都是完成验收条件所必需。不要把无关重构、架构升级和性能调优塞进同一任务。

涉及持久化、认证、授权、租户或项目数据时，先识别并保留数据隔离与一致性不变量。安全边界、权限绕过、不可恢复的数据损坏、核心服务无法启动或主用户流程完全不可用，不能以“先交付”为由延期。

## 问题优先级

- **P0：** 数据泄漏、权限绕过、严重数据损坏、服务无法启动、主流程完全不可用。立即处理。
- **P1：** 当前功能核心路径失败、公开接口契约错误、稳定复现的关键逻辑或回归故障。当前功能完成前处理。
- **P2：** 次要边界、非关键 UI 或性能问题、少量非阻塞重复。记录技术债后继续当前目标。
- **P3：** 抽象美化、提示词微调、极限性能或缺少基准支撑的优化。进入专项阶段再处理。

P0/P1 的处理优先于常规调试预算。P2/P3 不应因为理论上还能改善就扩大当前任务。

## 验证、调试与完成

先从变更的行为、契约和风险推导验证范围，并在执行前选定最小的有效命令：

| 时点 | 验证范围 |
|---|---|
| 开发中 | 受影响的单元、契约、集成路径；修复后只重跑相关失败项和必要的相邻回归。 |
| 功能完成 | 当前模块的相关测试，加上相邻模块的关键回归；涉及多模块时覆盖受影响的各模块和跨模块不变量。跨模块本身不触发全量测试。 |
| 里程碑、发布、明确门禁或定向验证无法圈定的具体风险 | 按用户要求、当前任务计划、仓库门禁或实际风险执行全量测试及适用的 PostgreSQL、契约、静态或浏览器检查；通常在最终检查点执行一次，计划另有规定则依计划执行。 |

CI 在 PR 中运行全量测试；同一提交的 CI 已通过时，除非计划明确要求本地执行或仍有未解决风险，避免在本地重复同一全量门禁。决定跑全量前，说明触发它的要求或风险和执行时机。端到端验证覆盖本次关键旅程；失败时先区分产品故障、环境问题和 flaky 行为。不要为让测试变绿而扭曲正确的业务语义。

测试失败、复现不稳定或连续修复无效时，按 [问题分级与调试流程](references/triage-and-debug.md) 操作。涉及 RAG、Memory、Token、延迟或并发调优时，按需读取 [评测与优化流程](references/optimization.md)。

如果出现值得修但不阻塞当前目标的问题，记录在 `docs/tech-debt.md`；文件不存在时再创建。记录状态、影响、触发条件、临时方案、延期原因、后续验证方法和建议阶段。不要把敏感正文写入生产日志；AI 或检索链路只记录经过脱敏的指标与稳定标识。

功能满足验收条件、没有未处理的 P0/P1、对应阶段的验证已完成且延期项已记录后即可结束。用户指令、具体任务计划和 CI 门禁要求的验证仍须完成；本技能不把全量测试附加到普通局部改动上。不要主动扩大已完成任务的范围。

技能调用示例与维护约定见 [项目 Agent skills 使用与维护](../../../docs/agent-skills.md)。
