# AI 质量与性能评测流程

只有在主流程可用且问题有测量依据时，才进入专项调优。推荐按功能加固、AI 质量评测、成本与延迟、目标负载并发的顺序推进；阶段可按项目里程碑调整，不需要为每个日常功能完整执行。

## RAG

先准备覆盖真实问题类型的评测集，再逐次改变一个主要变量。按适用性观测 Recall@K、MRR/NDCG、答案依据充分性、检索延迟和上下文 Token。依次考察分块策略、embedding、top-k、metadata filter、混合检索、reranker 和上下文压缩；没有评测结果时不要凭感觉追求某个参数最优。

## Memory

重点验证用户和项目命名空间隔离、错误召回、过期信息与相似内容干扰。用对照用户、对照项目和相似查询检查 false recall、跨域泄漏、过期记忆及错误个性化。记录稳定 ID 与汇总指标，不把记忆正文写进生产日志。

## Token 与延迟

先拆分 system、memory、RAG、历史对话、tools、user 和输出成本，再优先处理实测占比最高的来源。延迟按 intent、memory、retrieval、rerank、LLM、tools 和 response 分段观测；优化最大耗时段，并复测质量和成本是否回退。

## 并发与扩展

使用明确的目标负载测量 p50/p95/p99、吞吐、错误率、连接池、CPU、内存、限流和排队时间。先确认瓶颈，再决定是否引入缓存、队列、worker、batching 或水平扩展。不要在没有 workload 和测量结果时预先增加基础设施。

专项评测不能绕过安全和数据隔离要求。只有与当前验收目标直接相关时，才把调优并入日常功能任务。

## 可观测性与隐私

在对应链路新增或修改时，保留足以定位成本与质量的非敏感字段：

- LLM：模型、路由、延迟、输入/输出/总 Token、估算费用（可得时）、fallback。
- RAG：检索延迟、top-k、chunk 稳定 ID、分数、上下文 Token；不要记录原始敏感 query。
- Memory：脱敏 namespace、opaque user/project ID、类型、召回数量和稳定 ID、延迟。
- API：endpoint、延迟、状态码、request ID 和错误类型。

不要记录原始提示词、学习资料正文、记忆正文、凭据或其他生产敏感内容。
