# 问题分级与调试流程

## 每次失败先收集证据

1. 判断问题是否由本次改动引入。
2. 保留失败命令、最短相关错误信息和复现条件。
3. 提出一个可验证的根因假设。
4. 一次只验证一个假设，采用最小改动。
5. 修复后只运行最相关的验证，再判断是否需要扩大范围。

不要顺手重构无关模块，不要一次改多个互不相关的原因，也不要仅为满足测试断言改变正确业务行为。

## 调试预算

- 普通单元测试问题：通常不超过 2 次有明确假设的针对性修复。
- 集成问题：通常不超过 3 次根因尝试。
- 端到端问题：先检查服务状态、数据、浏览器时序、测试夹具和环境，再判断是否修改产品代码。

这些次数是避免无依据地反复 patch 的默认界线，不是忽略 P0/P1 的理由。如果达到预算仍未解决，停下来重新分析证据与根因。属于 P2/P3 时记录为技术债并继续当前里程碑；属于 P0/P1 时继续调查，但先修正诊断方向或补充能区分假设的证据。
